# Topic 4: Version Control with Git and GitHub

---

## Why Version Control Matters

As you move from writing simple Python scripts to orchestrating complex AI applications, the stakes get higher. You will write code, break it, fix it, and eventually want to share it.

Without version control, developers often resort to saving files like this:
- `script.py`
- `script_v2.py`
- `script_final.py`
- `script_final_actually_working.py`

This is unmanageable. **Version Control** solves this by:
1. **Never losing working code:** You can always "time travel" back to a previous state if you break something.
2. **Tracking changes:** It records *what* was changed, *when*, and *why* (via commit messages).
3. **Collaboration:** It allows multiple people to work on the exact same codebase without overwriting each other's work.

---

## Git Fundamentals

**Git** is the industry-standard version control software that runs locally on your machine. 

To use Git effectively, you need to understand four core concepts:
1. **Repository (Repo):** A folder on your computer that Git is tracking. It contains your project files and the hidden `.git` folder holding the entire version history.
2. **Commit:** A snapshot of your project at a specific point in time. Think of it as a "save point" in a video game.
3. **Branch:** An independent line of development. You can create a branch (e.g., `feature-add-ai`) to safely experiment without affecting the main working code (the `main` branch).
4. **Merge:** The act of taking the changes from one branch (e.g., your experimental feature) and combining them back into another branch (e.g., `main`).

## The GitHub Workflow

While **Git** is the software running on your computer, **GitHub** is a cloud-based hosting service for Git repositories. It serves as your remote backup, portfolio, and collaboration hub.

The standard day-to-day workflow looks like this:

1. **`git clone <url>`**: Downloads a repository from GitHub to your local machine.
2. **Make your code changes**: (e.g., creating a Python script that calls the Anthropic API).
3. **`git add <file>`**: Tells Git to stage your modified files, getting them ready to be saved in the next commit.
4. **`git commit -m "Your message"`**: Takes the snapshot of the staged files and permanently saves them to your local history.
5. **`git push`**: Uploads your local commits to the remote repository on GitHub so they are backed up and visible to others.

## Folder Structure and README

A professional codebase is highly organized. When someone visits your GitHub repository, they shouldn't have to guess how your project works.

**Standard Project Structure:**
```text
my-ai-project/
├── data/                  # Raw and processed datasets
├── src/                   # Source code (Python files)
├── tests/                 # Unit tests
├── .gitignore             # Tells Git which files to ignore
├── requirements.txt       # List of Python dependencies (like 'anthropic')
└── README.md              # The front page of your project
```

**The README.md** is arguably the most important file in your repository. It should explain:
- **What** the project does.
- **How** to install it (e.g., `pip install -r requirements.txt`).
- **How** to run it (e.g., `python src/main.py`).

## .gitignore: Protecting Your Secrets

In Week 12, we learned that leaking your Anthropic API key is a massive security risk. If you push a Python file containing your hardcoded API key to a public GitHub repository, automated bots will scrape it and rack up thousands of dollars in charges on your account within minutes.

To prevent this, you use a **`.gitignore`** file. This is a simple text file placed in the root of your repository. Any file or folder name listed inside `.gitignore` will be completely ignored by Git and never uploaded to GitHub.

**Example `.gitignore`:**
```text
# Ignore environment variable files containing API keys
.env

# Ignore Python cache files
__pycache__/

# Ignore virtual environments
venv/
```

By placing your API key in an ignored `.env` file and loading it into Python using `os.getenv()`, your code remains safe to share publicly.

## Commit Discipline

Finally, becoming a professional developer means writing clean, disciplined commits. 

1. **One Logical Change per Commit:** Do not work for 12 hours straight and commit 50 unrelated changes with the message `"did some work"`. If you added a new prompt template, commit that. If you fixed a bug in the JSON parser, make that a separate commit.
2. **Meaningful Commit Messages:** A commit message should complete the sentence: *"If applied, this commit will..."*
   - Bad: `fixed stuff`
   - Good: `Add retry logic to Anthropic API call`
   - Bad: `update`
   - Good: `Update system prompt to require JSON output`
