# Professional Coding Discipline

---

## Why Coding Discipline?

In the previous units, you learned how to write code to make a machine do what you want — storing data, making decisions, and repeating actions. However, writing code is only a fraction of a professional software engineer's job. The rest is about ensuring that the code you write actually solves the right problem, behaves predictably, and doesn't break when unexpected data is thrown at it. 

This unit shifts focus from *how* to write code to *how to think* about writing code. These habits separate junior coders who guess their way to a solution from AI-native engineers who design robust, reliable systems. Mastering these disciplines early will save you hours of debugging and make you a highly effective developer.

**Quick glossary:**

| Term | Meaning |
|---|---|
| **Specification (Spec)** | A plain-English description of what a program must do, its inputs, and its expected outputs. |
| **Happy Path** | The execution path where everything goes perfectly (valid inputs, no errors). |
| **Edge Case** | A situation that occurs at the boundary of expected inputs (e.g., an empty list, zero, maximum allowed value). |
| **Invalid Input** | Data that completely violates the expected type or format (e.g., text when a number was expected). |
| **Robustness** | A measure of how well a program handles edge cases and invalid inputs without crashing. |

---

## Spec-First Discipline

A **specification** (or "spec") is a plain-English description of exactly what a piece of code needs to do, what inputs it will receive, and what outputs it should produce. **Spec-first discipline** means you never write a single line of Python, nor do you prompt an AI to write it for you, until you have written out the specification. If you cannot explain the logic in simple English, you cannot write it in code.

Without a spec, beginners often fall into the "guess-and-check" trap — tweaking code blindly until it looks like it works. When working with AI, asking for code without a strict spec leads to hallucinations, overly complex solutions, or code that solves the wrong problem. A spec acts as a blueprint that keeps both you and the AI on track.

**Example: A Vague Prompt vs. A Spec-First Prompt**

*Bad (No Spec):* "Write a program for ticket discounts."
*Good (Spec-First):* "Write a Python program that asks for a user's age. If the age is under 12, print 'Child discount'. If the age is 65 or older, print 'Senior discount'. Otherwise, print 'Standard ticket'. Handle edge cases where the age is exactly 12 or exactly 65."

---

## The Golden Rule

**The Golden Rule:** Never run code you cannot explain line by line.

In the era of AI coding assistants, it is incredibly easy to generate 50 lines of complex Python instantly. If you paste that code and run it without understanding it, you become a liability. When that code inevitably breaks in production (and it will), you will have no idea how to fix it because you never understood it in the first place. You must maintain ownership of the logic.

## Edge Cases

An **edge case** is a problem or situation that occurs only at an extreme (maximum or minimum) operating parameter. It involves testing what happens at the boundary of expected input. For example, if a program asks for a positive number between 1 and 10, the "happy path" is entering `5`. The edge cases are entering exactly `1` or `10`. Invalid inputs are entering `0`, `11`, or `"apple"`.

**Example: Identifying Edge Cases**

If a program validates a password that must be exactly 8 characters long:
- **Happy Path:** "Password123" (11 characters — wait, that fails. Let's say "Pass1234" which is 8 characters).
- **Edge Cases:** A password that is exactly 7 characters, or exactly 9 characters. 
- **Invalid Input:** An empty string `""`.

## Applying Discipline to Your Python Foundations

You must apply these principles directly to the core Python concepts you learned earlier this week:

- **Variables & Input:** When using `input()`, users will invariably type the wrong thing (like entering `"ten"` instead of `10`). A professional anticipates this instead of assuming the happy path.
- **Conditionals:** When writing `if/elif/else` statements, you must test the exact boundaries. If you check `if age > 18`, you must deliberately test what happens when `age` is exactly `18` to prevent logic gaps.
- **Loops:** When writing a `while` loop, the edge case is the condition never changing, resulting in an infinite loop. The Golden Rule means you must trace the loop's execution manually to ensure the termination condition is reachable.

## Real-World Application

- **Banking & FinTech:** An edge case in a withdrawal system is withdrawing exactly $0, or withdrawing an amount that leaves exactly $0.00 in the account. Missing this edge case could lead to division-by-zero errors or locked accounts.
- **E-commerce:** A user applying a discount code that makes the cart total negative. A robust system catches this edge case and caps the discount at 100% of the cart value.
- **AI/ML:** Sending an empty string, or a string with 10,000 characters, to an LLM prompt. A spec-first approach ensures the code checks the length of the input before making the expensive API call.
- **Healthcare:** A heart rate monitor software must handle edge cases where the sensor temporarily returns `0` or `null` due to a loose wire, rather than assuming the patient has flatlined.

## Try it Yourself (Worked Example)

### Problem Statement

You are asked to write a program that calculates shipping costs based on package weight. The specification is: 
"Packages under 2 kg ship for $5. Packages exactly 2 kg up to 5 kg ship for $10. Packages over 5 kg are not accepted. Determine the boundary edge cases and write the logic, ensuring you can explain every line."

### Step 1: Plan the Solution & Identify Edge Cases

Before writing code, we must identify the edge cases to test:
- **Happy Paths:** `1.5` kg ($5), `3.0` kg ($10)
- **Edge Cases (Boundaries):** exactly `2.0` kg (should be $10), exactly `5.0` kg (should be $10), exactly `5.1` kg (should be not accepted).
- **Invalid Inputs/Extreme Edge Cases:** exactly `0` kg, negative weights like `-1` kg (should definitely not be accepted or should throw an error).

### Step 2: Write the Python Code

```python
weight = float(input("Enter package weight in kg: "))

if weight <= 0:
    print("Invalid weight. Must be greater than 0.")
elif weight < 2:
    print("Shipping cost: $5")
elif weight <= 5:
    print("Shipping cost: $10")
else:
    print("Package exceeds maximum weight of 5 kg and is not accepted.")
```

### Step 3: Explain Each Line (The Golden Rule)

- `weight = float(input(...))` — Prompts the user for a weight, reads it as text, and converts it to a decimal number (`float`).
- `if weight <= 0:` — Protects against the extreme edge case of zero or negative weights.
- `elif weight < 2:` — Handles the first tier (under 2 kg). We use `< 2` so that exactly 2 kg falls to the next condition.
- `elif weight <= 5:` — Handles the second tier. Because we already checked `< 2`, this branch only catches weights from 2.0 up to and including 5.0.
- `else:` — Catches anything over 5.0 kg.

## Common Mistakes

- **Prompting AI vaguely:** Asking "write a login script" instead of providing a spec ("Write a login script that takes a username and password, checks if the password is at least 8 characters long, and returns a boolean").
- **Blind Copy-Pasting:** Copying code from an AI or StackOverflow and running it immediately without reading it.
- **Testing only the happy path:** Assuming users will always type exactly what you expect and never testing what happens when they don't.

## Interview Questions

**Q1: "How do you test your code?"**

A: Interviewers don't just want to hear "I run it." They want to hear that you proactively identify **edge cases** and boundary conditions. Mentioning that you test the "happy path, the edge cases, and invalid inputs" demonstrates professional maturity.

**Q2: "How do you use AI to help you code?"**

A: The correct answer is heavily rooted in the **Golden Rule** and **Spec-First discipline**. Explain that you write a clear English specification first, prompt the AI, and then read the generated code line-by-line to verify it matches your spec and handles edge cases, rather than blindly copy-pasting.

---

## Quick Recap

- **Spec-first discipline** forces you to define the problem in plain English before writing or generating any code, serving as a blueprint for success.
- **The Golden Rule** dictates that you must never run code you cannot explain line by line. You must maintain ownership of the logic, especially when using AI tools.
- An **edge case** occurs at the boundary of expected inputs (like `0`, maximum limits, or empty data). 
- Professional developers always test the **happy path**, **edge cases**, and **invalid inputs** before considering a feature complete.
- Robust code is code that anticipates bad inputs and handles them gracefully without crashing or producing incorrect results.
