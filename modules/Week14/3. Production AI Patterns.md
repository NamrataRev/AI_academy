## Moving from Prototype to Production

Building a cool AI script that works on your laptop is relatively easy. Building an AI system that serves thousands of users concurrently without crashing, going over budget, or taking 30 seconds to answer is incredibly difficult. 

When you move an AI application into **Production** (live, real-world usage), every architectural choice you make is a balancing act between three competing factors: **Cost, Latency, and Reliability**.

### The "Iron Triangle" of Production AI

1. **Cost:** How much are you paying per API call? Advanced models (like Claude 3.5 Sonnet or GPT-4o) cost significantly more than smaller models (like Claude 3 Haiku or GPT-4o-mini). RAG systems also cost more because you pay for the tokens in the retrieved documents you inject into the prompt.
2. **Latency:** How long does the user have to wait for a response? A complex agent loop might take 45 seconds to finish thinking, which is unacceptable for a customer service chatbot but perfectly fine for a background research task.
3. **Reliability:** How often does the system fail, hallucinate, or return improperly formatted data? Highly constrained prompts and retry loops increase reliability but add to latency and cost.

You cannot maximize all three. If you want the highest reliability, you will likely increase cost and latency by using a larger model and complex validation loops.

---

## Standard Production AI Patterns

To manage these trade-offs, engineers rely on established architectural patterns. 

### 1. The "Router" Pattern
Instead of sending every request to your most expensive model, use a very cheap, fast model (the Router) to classify the user's intent first.
- **How it works:** User asks a question -> Fast model classifies it as "Small Talk" or "Complex Math" -> If small talk, the fast model handles it. If complex math, the system routes the request to an expensive, advanced model.
- **Trade-off:** Slightly increases latency on the first step, but drastically reduces overall costs while maintaining high reliability for hard questions.

### 2. The "Fallback" (or Cascading) Pattern
APIs go down. Rate limits get hit. You need a backup plan.
- **How it works:** Your system attempts to call the primary model (e.g., Anthropic). If it fails due to a network error, your `except` block automatically calls a backup provider (e.g., OpenAI or Google Gemini).
- **Trade-off:** Maximizes reliability.

### 3. Asynchronous Background Processing
If you are running an AI Agent that takes a long time to think, do not make the user stare at a loading spinner.
- **How it works:** The user submits a request. The system immediately replies, "We are working on your report and will email it to you in 5 minutes." The AI Agent runs on a background server.
- **Trade-off:** Eliminates latency from the user's perspective, but increases backend engineering complexity.

## Writing an Architectural Decision

Because there is no single "correct" pattern, professional engineering teams use **Architectural Decision Records (ADRs)**. An ADR is a short document that explains *why* a specific pattern was chosen over the alternatives. 

Writing an ADR forces you to critically analyze the trade-offs before you write any code.

### Example ADR: Choosing an AI Pattern for a Customer Support Bot

**Context:** We are building a chatbot for our e-commerce website to handle customer returns and product questions.

**Options Considered:**
1. Use an autonomous AI Agent to handle all customer interactions and initiate refunds.
2. Use a direct LLM call with a massive system prompt containing all company policies.
3. Use a RAG pattern with a smaller, faster model (Claude 3 Haiku) to search policy documents.

**Decision:** We will use **Option 3 (RAG with a fast model)**.

**Justification:**
- **Cost & Latency:** Option 2 (massive prompt) would be too expensive and slow because we would pay for 10,000 tokens of policy text on every single user message. Option 3 retrieves only the relevant paragraphs, keeping latency under 2 seconds and costs minimal.
- **Reliability:** Option 1 (Autonomous Agent) poses an unacceptable risk; we cannot allow an AI to autonomously approve refunds (an irreversible action). Option 3 grounds the model in retrieved facts, ensuring it quotes the actual return policy rather than hallucinating.

By documenting this decision, any new engineer joining the team immediately understands the logic behind the system's architecture.
